## Interlock / UI enhancements

Requested 2026-08-05, while starting Phase 5. Likely natural fits for Phase 6 ("interlock bounds/rate-limit checks vs. AI + decision log UI") since that's the next planned decision-log-UI touchpoint, but could be done ad hoc whenever.

- [ ] **1. Decision log: show more history.** Currently hardcoded to the last 15 ticks (`DECISION_LOG_ROWS` in `app.py`) — user wants substantially more visible (they were seeing ~20 with the scrollable table). Simplest fix is just raising the constant; consider whether the full `st.session_state.history` (rolling buffer, currently 500 ticks) should be viewable/scrollable rather than a fixed recent-N slice.

- [ ] **2. Manual "reset interlock" action.** Right now, once the sensor-trust gate trips (`sensor_trusted=False`), the *only* way it clears is the detector's own flags naturally going false again (CUSUM decaying, stuck fault manually toggled off long enough to rebuild a non-flat window, etc.) — there's no operator action to say "I've confirmed it's safe, resume normal control." This is a real, common real-world pattern (alarm acknowledgment in SCADA/DCS systems) worth adding. Needs design thought when implemented: does it force-clear the detector's internal state (window/CUSUM) outright, or just override the trust gate for one cycle and let the detector keep evaluating normally from there? Should probably log this distinctly as an operator-acknowledged reset, not conflated with a normal detector-clears event or with the existing bounds-override mechanism (which is a different concept — overriding a *specific rejected proposal*, not clearing a sustained distrust state).

- [ ] **3. Auto-safe-default after sustained interlock activation.** If the interlock has been continuously holding/rejecting (sensor untrusted) for 20 seconds, automatically command the heater to a safe default (almost certainly 0%, given this system has no active cooling) rather than continuing to hold indefinitely at whatever value happened to be "last-known-good" when the trip occurred. This is structurally the same dead-man-timer pattern the doc already specifies for AI failure handling (§3.6: hold → 10s warning → auto safe default), just triggered by sustained sensor distrust instead of AI unresponsiveness — Phase 5's AI failure-handling implementation may end up sharing most of this machinery, worth building them together or at least consistently. Should log as a system-initiated safety action, distinct from any human-initiated action, per doc §3.6's own framing.

- [ ] **4. Escalate the hard over/under-temperature trip to a latching lockout after repeated firings without correction.** Requested 2026-08-05, in direct response to confirming the trip (added post-Phase-5) is currently self-clearing (fires fresh off `t_sensed` every tick, no stored "tripped" state) — real industrial high-high trips often latch specifically so an operator can't ride the temperature back and forth across the limit unattended. User's proposal: if the trip fires **N times** (variable, default **2**) **without the actuator value changing** in a way that would actually bring the temperature back down, stop returning control to the active controller at all until something clears it. Several open design questions to resolve before implementing, worth a design discussion first rather than guessing:
  - **What counts as "fires N times"** — N separate trip *episodes* (temperature drops back under the threshold between them, then crosses again), or N consecutive *ticks* while still tripped? Episodes seems like the more sensible reading of "without correction" — it's about the controller failing to learn across repeated excursions, not about a single sustained excursion lasting a while.
  - **What counts as "a change in actuator value to bring temperature back down"** — does the controller need to propose something below the trip's forced safe value between episodes, or just *any* different value, or specifically a value trending toward 0? This determines whether a controller that's genuinely trying (just too slowly) gets locked out the same as one that's proposing the same bad value repeatedly.
  - **What does "before it allows a new control" mean mechanically** — a full lockout that force-holds at the safe value and refuses every proposal from any controller (not just the one that caused it) until an explicit operator action clears it? This is essentially the *latching* variant of item 2 above — the two are almost certainly meant to be built together, since a latch with no way to clear it isn't useful. Should log the lockout itself as a distinct, escalated event in the decision log, separate from an ordinary trip.

- [ ] **5. Sensor-trust "hold at last-known-good" can itself hold at an unsafe value.** Requested 2026-08-05. If the last actuator value before the sensor-trust gate tripped was large (controller was actively heating hard right when the detector flagged something), the interlock freezes there and keeps applying it every tick for the entire untrusted period — temperature keeps rising the whole time, since "hold" isn't the same as "safe." This is a real, currently-unaddressed gap, and it's sharper than it looks because of a deliberate ordering decision made when building the hard trip (item 4's trip, see also `CLAUDE.md`'s Post-Phase-5 section): the sensor-trust gate is checked *first* and short-circuits, so the hard over-temperature trip **never even runs** while the sensor is untrusted (`test_sensor_untrusted_takes_priority_over_hard_trip` locks this in directly) — reasoning at the time was "don't make a temperature-based decision on a reading you've already flagged as unreliable." That reasoning holds for *routine* control decisions, but arguably doesn't for a trip that only ever forces things toward *safer* (heater off) — if the untrusted reading is wrong, forcing off is still safe; if it's right, forcing off is clearly correct either way. Worth a real design discussion, not a quick fix: does the hard trip get an exception to run even while untrusted (since it's one-directional and can't be manipulated into a worse outcome), does "hold at last-known-good" get capped at some conservative ceiling instead of literally whatever was last applied, or something else? Connects to item 3 above (time-based auto-safe-default) but is a different trigger — this is about the *held value itself* being unsafe, not about how long it's been held.
